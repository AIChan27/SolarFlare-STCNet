# 第零部分 · 结论速览

| 问题 | 结论 |
|---|---|
| 这次实验数据正常吗？ | **正常，但"优于论文"的说法已被多种子实验推翻**：单次 TSS 0.8477，**5 种子均值 0.8321 ± 0.0231**，与论文 0.8251 统计上不可区分 |
| 早停的原因 | **不是"提前"停，是正好跑满耐心值**：最优 Epoch 4，连续 10 轮未提升（`PATIENCE=10`），Epoch 14 触发 |
| 是过拟合吗？ | **有过拟合，但不是主因**。主因是**验证集太小（483 正样本）+ 噪声大导致最优模型选择不可靠** |
| 换 Tesla P40 会更快吗？ | **不会，大概率更慢**。5070 Laptop 的 FP32 算力约为 P40 的 1.9 倍，且支持 BF16/TF32（P40 不支持） |
| 换掉 1D-CNN 会有提升吗？ | **预计提升 ≤0.01，甚至可能变差**。该分支只占全模型 **0.37%** 的参数（103,490 / 27,638,012） |
| **多种子做完了吗？** | ✅ **已完成（5 种子）**，见 1.5 节。**TSS = 0.8321 ± 0.0231** |
| **最优 epoch 是哪一个？** | ⭐ **5 个种子的最优 epoch 全部在 Epoch 1–3**（D4 已完成）。**"第 1-3 轮就过拟合"是普遍规律，不是运气**——见 1.5.5 节 |
| **最该先做什么（已更新）** | **P1 阈值选择**：AUC 极稳（0.9664 ± 0.0029）而 TSS 波动大（±0.0231），**证明波动来自阈值而非模型** |
| **导师要的交叉注意力能做吗？** | ✅ **能，而且方向正确**。但需先解决 320 维 vs 32 维的维度错配，见第六部分 |
| **导师问的其他创新点？** | 见第七部分，7 个候选（其中 #2 时间到耀斑多任务、#3 交叉注意力物理验证 最适合） |
| **导师给的数据集（JW-FD）？** | ⭐ **最高优先级**。27× 样本、29 特征、跨两个活动周，**一次解决我们确诊的三个瓶颈**，见 4.4.0 节 |
| 当前 46 秒/epoch 还有优化空间吗？ | **数据加载已优化到底**（98ms → 9ms），46 秒≈纯 GPU 计算时间，接近理论下限 |

> **给项目组的一句话（已按 5 种子实验修正）**：
> 我们的 STCNet 复现已达到 **TSS = 0.8321 ± 0.0231**（5 种子），与论文的 **0.8251** **统计上不可区分**——是"追平"，不是"超越"。
> 关键的诊断结论是：**模型判别能力已经稳定（AUC = 0.9664 ± 0.0029），TSS 的波动主要来自固定的 0.5 阈值，而不是模型能力。**
> 所以下一步的重点**不在"换更花哨的模型"**，而在三件事：**① 把决策规则（阈值/校准）做对；② 在数据层面找增量（JW-FD 的 27 倍样本）；③ 做能提供不可替代分析价值的工作（交叉注意力的物理可解释性）。**

**与论文的差异（3 处，都需要在论文里说明）**

| 项目 | 论文 | 本项目 | 原因 |
|---|---|---|---|
| 数据集正样本总数 | 3184 | **2988** | 论文数字疑有误。实测负样本 70822 与论文**完全一致**，正样本差 **196**（恰好等于论文自己的测试集正样本数）。但论文又称训练集正样本 = 2988 = 全集正样本，两者不能同时成立 |
| 训练集 | 正 2988 / 负 5073 | 正 2358 / 负 4342 | 我们额外切出 483 正样本作验证集（论文没提验证集） |
| 测试集 | 正 196 / 负 11852 | 正 147 / 负 11963 | 论文时间段切分后实测值，边界日期取闭/开区间会造成差异 |

> **验证集为什么取 2015 年**：实测论文训练段 B（2017-09 ~ 2019-01）的 **49 个正样本全部集中在 2017-09 这一个月**，2017-10 之后一个正样本都没有（太阳活动极小期）。用它做验证会得到 0 正 / 187 负的单类别数据集，TSS 恒为 0、早停完全失效。改用训练段 A 的尾部后验证集正负比 1:1.5，训练集仅损失 17% 正样本。详见 [`dataset_build.md`](../notes/dataset_build.md) 第五节。

### 1.5.4 结论 3：⭐ **波动来自阈值，不是来自模型**（本次最重要的发现）

这个发现是本次实验最有价值的产出，看这两行对比：

| 指标 | mean ± std | 相对波动（std/mean） |
|---|---|---|
| **AUC**（阈值无关） | **0.9664 ± 0.0029** | **0.30%** ← 极稳 |
| **TSS**（依赖阈值 0.5） | 0.8321 ± 0.0231 | **2.78%** ← 波动是 AUC 的 **9 倍** |

**AUC 几乎不动，但 TSS 在 0.7936 ~ 0.8548 之间跳（极差 0.061）。** 这个组合只有一个解释：

> **五个种子的模型判别能力（排序能力）几乎完全相同，差别只出在"0.5 这个阈值切在哪里"。**

进一步验证这个解释——看 seed 2 这个"异常"样本：

```
seed 2 :  AUC = 0.9641（接近均值）  但 TSS = 0.7936（最低）
          TPR = 0.8571（最低）      FAR = 0.0635（最低）
          → 模型偏保守：阈值 0.5 时把很多真耀斑判成了负类，但虚报也最少
```

**seed 2 的模型并不差（AUC 正常），只是它的概率分布整体偏低**，导致固定阈值 0.5 切得偏保守。如果给它单独选一个更低的阈值，TSS 大概率会回到 0.83 以上。

**实际含义（直接影响后续优先级）**：

| 推论 | 说明 |
|---|---|
| **① 阈值选择可以"零成本"提高 TSS 并降低方差** | 每个种子在**验证集**上选最优阈值，再固定到测试集评估 → 预期能同时**抬高均值**和**压缩 std** |
| **② 模型架构改进的空间被高估了** | 如果 AUC 已经 0.9664 ± 0.0029，说明模型"看到"的信息基本到位了，**瓶颈更可能在决策规则和数据标签，而不是网络结构** |
| **③ "微小改进"必须用 AUC 来筛查** | 如果某个改动只让 TSS 动了 +0.01 而 AUC 没动，那多半只是阈值巧合，不是真改进 |

> **由此，后续优先级应调整为：P1 阈值选择 > P2 消融实验 > P3 架构改动。**
> 这也恰好呼应导师提的"交叉注意力"——架构改动要谨慎，先确认决策规则是否已经最优。

**发现 3：训练 loss 持续下降，验证指标再也没好转**

**发现 4：对后续措施的直接指导**

| 措施 | 为什么现在更有把握 |
|---|---|
| **冻结主干前几层** | 过拟合在 **Epoch 1** 就已开始，说明**预训练特征被"覆盖"得太快**。冻结底层最能防止这一点，是针对性最强的措施 |
| **提高 dropout（0.3 → 0.5）** | 同理，正则化不足会让模型 1-3 轮就记住训练集 |

| **早停判据改滑动平均** | 最优总在前 3 轮，`PATIENCE=10` 其实**偏长**——它让后面 10 轮白跑。不影响最终结果，只影响训练时间 |
| ✅ **JW-FD（27 倍样本）** | ⭐ **这才是根本解**。容量/数据比是问题根源，只有加数据能改变这个比例 |

> **⚠️ 对 1.7 节"过拟合分析"的重要补充（判断被部分修正）**：
> 原来我判断"**验证集太小是主因**"，D4 的结果**修正了这个判断**——
> 1. **过拟合确实存在，且发生得极早（第 1-3 轮）** → 这是**容量/数据比**问题，需要正则化或更多数据；
> 2. **验证集小（483 正样本）只是让"选哪个 epoch"不可靠** → 这是**模型选择**问题，需要多种子；
>
> **两者是不同的问题，之前把它们混在了一起。** D4 让"**需要更多数据（JW-FD）**"这个结论的证据强度大幅提升。

## 1.6 答疑 1：这些数据正常吗？

### 单次运行的结论（**已被修正，仅供参考**）

### 结论：正常，而且是一次**很成功**的训练

四个关键指标**全部优于论文**：

| 指标 | 本次结果 | 论文 STCNet | 对比 |
|---|---|---|---|
| **TSS** | **0.8477** | 0.8251 | ✅ 高 0.0226 |
| TPR（报准率） | 0.9388 | 0.9227 | ✅ 高 0.0161 |
| **FAR（虚报率）** | **0.0910** | 0.0976 | ✅ **低** 0.0066 |
| TNR | 0.9090 | 0.9024 | ✅ 高 0.0066 |
| ACC | 0.9093 | 0.9027 | ✅ 高 0.0066 |
| F1 | 0.2009 | 0.1463 | ✅ 高 0.0546 |
| AUC | 0.9720 | — | — |

**"TPR 和 FAR 同时改善"是关键信号**：分类任务里通常提高报准率就要牺牲虚报率（ROC 曲线上是此消彼长）。两者同时变好，说明模型确实学到了有效特征，而不是靠调阈值换来的表面提升。

### 但有 3 点必须正确理解，否则会误判

#### ⚠️ 第 1 点：Precision = 0.1125 看着低，是**任务性质决定的**

测试集正负比 **147 : 11963 ≈ 1 : 81**。极端不平衡下 Precision 天然很低：

$$\text{Precision} = \frac{TP}{TP+FP} = \frac{138}{138+1089} = 0.1125$$

换个说法：**模型从 81 个活动区里找出 1 个真耀斑，容忍 8 个误报**。这在空间天气预报的业务场景里是**合理甚至偏保守**的——漏报（FN=9）的代价远高于虚报（FP=1089）。论文自己的 F1 也只有 0.1463，同一量级。

> **判断这个任务的好坏，看 TSS / FAR / TPR，不要看 Precision 和 ACC。**

#### ⚠️ 第 2 点：ACC 0.9093 是**误导性指标**

一个"永远预测无耀斑"的傻瓜模型在这个测试集上能拿到：

$$\text{ACC}_{\text{傻瓜}} = \frac{11963}{12110} = 98.8\%$$

**比我们的 90.93% 还高。** 所以 ACC 在这里毫无参考价值（这也是我们在输出里标注"不平衡时虚高"的原因）。**TSS 才是应该看的**，因为它对样本比例无偏——论文 4.2 节也是这么说的。

#### ⚠️ 第 3 点（最重要）：**单次结果不足以支撑任何结论**

计算一下统计不确定性：

| 数据集 | 正样本数 | 一个正样本误判对 TPR 的影响 | TSS 抽样不确定性 |
|---|---|---|---|
| 验证集 | 483 | 0.0021 | **≈ ±0.029** |
| 测试集 | 147 | 0.0068 | **≈ ±0.082** |

**实测验证集 TSS 在 14 轮里从 0.6412 波动到 0.8255，极差 0.184。**

再看一个警示信号：

```
验证集最优 TSS = 0.8255
测试集     TSS = 0.8477   ← 比验证集还高 0.0223
```

**测试集优于验证集，本身就是"差异主要来自抽样噪声"的证据。**

> **实际含义**：我们的 0.8477 与论文的 0.8251 之间的差距（0.0226），**在统计上区分不出来**。所以正确的表述是"**达到了论文的同等水平**"，而不是"复现得比论文好"。
>
> **推论**：任何小于 ±0.08 的"改进"都无法用单次实验证明。**这是后面所有实验设计的前提约束。**

## 1.7 答疑 2：早停结束的原因是什么？是过拟合吗？

### 1.6.1 早停的直接原因：**不是"提前"停，是正好跑满耐心值**

完整时间线：

| 项目 | 值 |
|---|---|
| 最优 epoch | **Epoch 4**（`val_TSS = 0.8255`，14 轮中的最高点） |
| 最优之后的轮数 | Epoch 5 ~ 14，共 **连续 10 轮**都低于 0.8255 |
| `config.PATIENCE` | **10** |
| 触发条件 | `patience_counter >= PATIENCE` → `10 >= 10` ✅ |
| 实际触发点 | **Epoch 14 结束时** |
| 已保存权重 | Epoch 4（已实测验证，误差 0.0000） |

**所以早停机制工作得完全正确**——它在"连续 10 轮没进步"的那一刻停下。你看到的 14 轮不是"没跑完"，而是设计如此。

> **补充说明**：时间戳显示 `stcnet_best.pth` 写于 23:44:42，而训练历史和曲线写于 23:52:25，中间隔了 8 分钟。正常结束时这两个时间应该紧邻，所以那 14 轮很可能是在 Epoch 15 运行过程中被手动中断的。**但结论不变**：即使不中断，也会在 Epoch 14 触发早停，停在同一位置。

### 1.6.2 是过拟合吗？—— **有过拟合，但不是主因**

#### 过拟合的证据（确实存在）

| 现象 | 数据 |
|---|---|
| 训练 loss 持续下降 | 0.7091 → 0.5935（单调） |
| 训练 acc 持续上升 | 0.8464 → 0.8966 |
| **验证指标 Epoch 4 见顶后回落** | TSS 0.8255 → 0.7482；ACC 0.9081 → 0.8816；F1 0.8906 → 0.8496 |
| train/val 的 ACC gap | **−0.025**（首轮）→ **+0.015**（末轮），确实在扩大 |

**是的，存在过拟合**。典型特征：训练集越来越好，验证集在 Epoch 4 之后再没超过。

> ### ⚠️ 本节判断已被 D4 核对部分修正（见 1.5.5 节）
>
> **原来的判断**："最优 Epoch 4 很可能包含运气成分（孤立尖峰），主因是验证集太小。"
>
> **D4 核对 5 个种子后的修正结论**：
>
> | 判断 | 修正后 |
> |---|---|
> | Epoch 4 是不是"运气尖峰"？ | ❌ **不是**。5 个种子的最优 epoch 全部落在 **Epoch 1–3**（中位数 2），**"早期见顶"是普遍规律，不是运气** |
> | 过拟合存在吗？ | ✅ **存在，而且比原以为的更严重**——**第 1 轮就已经开始过拟合**（seed 1/2 的最优就是 Epoch 1） |
> | "验证集太小是主因"对吗？ | ⚠️ **部分对，但混淆了两个不同问题**：<br>① **过拟合早发** → 是**容量/数据比**问题，需要正则化或**更多数据**<br>② **验证集小** → 是**模型选择**问题，需要多种子<br>**D4 让"需要更多数据（JW-FD）"的证据强度大幅提升。** |
>
> **所以下面的"原因 2 是主因"应读作"原因 1 和原因 2 是两个独立问题，都要解决"。**

#### 但根因是 3 个因素的叠加，主因不是"模型太大"

**原因 1：27.6M 参数 vs 2358 个正样本（容量远超数据）**

```
模型总参数      : 27,638,012
训练集正样本    : 2,358
```

即使每次只更新 0.01% 的参数，也足够把训练集背下来。**更关键的是能定位到过拟合发生在哪个分支**：

| 分支 | 参数量 | 占比 |
|---|---|---|
| Swin 主干 | 27,534,522 | **99.63%** |
| CNN 参数分支 | 103,490 | **0.37%** |

在 2358 个正样本上微调一个 2753 万参数的主干，**过拟合几乎全部发生在主干上**。这直接说明：**去改那 0.37% 的 CNN 分支，对缓解过拟合毫无帮助**（这一点在 1.9 节会展开）。

**原因 2：验证集太小导致"最优模型选择"本身不可靠 ⭐ 主因**
这是被低估最严重的问题。验证集 1208 条里只有 **483 个正样本**：

- 单个正样本 = TPR 变动 0.0021
- 每轮 TSS 在 0.64 ~ 0.83 之间跳（**极差 0.184**）

而 `PATIENCE = 10` 要求"连续 10 轮不超过 0.8255"。**在一个噪声 ±0.03 的指标上，等 10 轮去追一个高点，本质上是在等噪声重新掷出一次好骰子。**

看 Epoch 4 的邻居就明白了：

```
Epoch 3 : val_TSS = 0.7179
Epoch 4 : val_TSS = 0.8255   ← 孤立尖峰
Epoch 5 : val_TSS = 0.7654
```

**它是一个孤立尖峰，很可能包含运气成分。** 所以"保存 Epoch 4"这个决策，有相当概率**不是选中了最好的模型，而是选中了验证集上最幸运的那一次**。

**原因 3：学习率已衰减到很小，训练接近饱和**

lr 从 2e-4 降到 2.5e-5（每 4 轮 × 0.5）。到 Epoch 13-14 时模型基本停止有效更新——loss 在 0.594 ~ 0.613 之间震荡，不再单调下降。所以后期**不是"越训越糟"，而是收敛到一个平台，只是这个平台略低于 Epoch 4 的尖峰**。

#### 缓解措施（按性价比排序）

| 优先级 | 措施 | 原理 | 预期效果 |
|---|---|---|---|
| **P0** | **多种子重复 + 阈值扫描** | 多种子取平均压掉验证噪声；阈值扫描避开 0.5 的非最优选择 | **最有效，零风险** |
| **P1** | **冻结主干前几层** | 过拟合在主干的 99.6% 上，冻掉底层（通用特征）只微调顶层 | 高 |
| **P2** | **提高 `dropout`**（0.3 → 0.5） | 直接加正则化 | 中 |
| **P3** | **改进早停判据** | 现在 10 轮耐心在 1208 条验证集上太宽松；改成对 `val_TSS` 做 3 轮滑动平均再比较 | 中（模型选择更稳） |
| **P4** | **加大 weight decay** | 原代码注释里就有 `weight_decay=5E-2`，我们用的是默认 `1e-2` | 中 |
| **P5** | label smoothing | 防止过度自信 | 低-中 |

> **一个反直觉的点**：这里早停触发得"太晚"（等满 10 轮）不是问题，因为 Epoch 4 之后确实再没超过。**真正的问题不在早停参数，而在验证集太小导致的最优选择不可靠。** 所以 P0（多种子）优先级最高。

## 1.8 答疑 3：换到 Tesla P40 会更快吗？

### 结论：**不会，大概率更慢**

| | 本项目 RTX 5070 Laptop | 论文环境 Tesla P40 | 谁强 |
|---|---|---|---|
| 架构 / 年份 | **Blackwell，2025** | Pascal，**2016** | **5070 新 9 年** |
| CUDA 核心数 | — | 3840 | — |
| FP32 算力 | ~23 TFLOPS | **12 TFLOPS**（官方标称） | **5070 快约 1.9×** |
| FP16 张量核心 | ~180 TFLOPS | **无张量核心** | **5070 压倒性** |
| **显存** | 12 GB GDDR7 | **24 GB GDDR5** | **P40 大 2×** |
| 显存带宽 | ~460-670 GB/s | **346 GB/s**（GDDR5, 384-bit） | **5070 高约 1.3-1.9×** |
| BF16 / TF32 支持 | ✅ | ❌（Pascal 全无） | **5070 独有** |
| 定位 | 消费级（可训练） | **数据中心推理卡** | 用途不同 |

**数据来源**：[NVIDIA Tesla P40 官方 Datasheet](https://www.nvidia.cn/content/dam/en-zz/Solutions/design-visualization/solutions/resources/documents1/nvidia-p40-datasheet.pdf)（12 TFLOPS FP32 / 47 TFLOPS INT8 / 3840 CUDA 核心 / 24 GB GDDR5）

**计算部分：5070 快接近一倍，而且优势比看上去更大。** P40 的"24 GB"是为**大 batch 推理**设计的，不是为算得快——它的定位是**推理加速卡**，官方宣传重点是"单卡替代 40 个 CPU"的推理吞吐，而不是训练性能。FP32 12 TFLOPS 在 2026 年是很低的水平；而且 Pascal 架构**没有张量核心、不支持 BF16/TF32**——这意味着后面如果加 AMP 混合精度，**P40 拿不到 Tensor Core 的加速，而 5070 能拿到**。

**数据加载部分：也未必更快。** 关键是**我们已经把数据加载从 98ms 优化到 9ms 了**（见下），它已经不是瓶颈。论文的 i7-10700（8 核 16 线程）与我们的 16 逻辑核在这个任务上差别不大。

### 46 秒/epoch 是怎么构成的

```
训练集 6700 条 ÷ 32 = 210 个 batch
验证集 1208 条 ÷ 32 =  38 个 batch
合计                  248 个 batch

248 × 195ms（GPU 前向+反向）≈ 48 秒   ← 与实测 46 秒吻合
```

**结论：46 秒已经接近这个任务的理论下限**——时间几乎全花在 GPU 计算上，没有浪费。而我们前面已经把数据加载的浪费挤掉了：

| num_workers | 单 batch 数据加载 | 相对加速 |
|---|---|---|
| 0（原始配置） | 98.2 ms | 1.00× |
| 2 | 38.9 ms | 2.53× |
| 4 | 22.0 ms | 4.45× |
| **8（当前配置）** | **8.6 ms** | **11.43×** |

端到端效果：**85 秒/epoch → 46 秒/epoch**（提速约 46%）。

> **所以：不要为了速度换设备。** 性能差异最多 2 倍，在方法学做扎实之前毫无意义。全量 50 epoch 在现在的机器上只要 40 分钟。唯一可能有意义的场景是**你想用 batch ≥ 128**（P40 的 24 GB 能放下，5070 的 12 GB 放不下），但这个任务 batch 32 已够用。
>
> **⚠️ 但论文的硬件描述可以借鉴一点**：论文用 P40 时，`num_workers` 的设置、以及是否用了 AMP，会直接影响它的 epoch 时间。如果我们要严格对比"训练成本"，需要知道论文的 batch size 和训练轮数——论文里没写。

## 1.9 答疑 4：把 1D-CNN 换成 LSTM/TCN/Mamba/Transformer 会有提升吗？

> 背景：项目组同学提供了一份模型选型表（整段分类 1D CNN/ResNet1D/Transformer；预测未来 TCN/LSTM/Transformer/ARIMA/Mamba；序列标注 BiLSTM-CRF；小数据 滑窗+GBDT；长序列 TCN/稀疏 Transformer/SSM；实时低延迟 因果 1D CNN/TCN），建议替换现有的 1D-CNN。

### 结论：**预计提升 ≤ 0.01，甚至可能变差。这不是模型问题，是任务形态不匹配。**

### 理由 1：那个分支只占全模型 0.37% 的参数

| 分支 | 参数量 | 占比 |
|---|---|---|
| Swin 主干 | 27,534,522 | **99.63%** |
| CNN 参数分支 | 103,490 | **0.37%** |

**你只替换 0.37% 的容量。** 无论换成 LSTM、Mamba 还是 Transformer，99.63% 的主干原封不动。

### 理由 2：那 10 个参数里**没有"序列"**

现在的数据流是：

```
一个样本 = 某活动区、某一时刻的一张磁图 + 该时刻的 10 个 SHARP 参数
标签     = 该时刻起未来 48h 内是否发生 M+ 耀斑
```

10 个参数是 **TOTUSJH、TOTPOT、TOTUSJZ、ABSNJZH、SAVNCPP、USFLUX、AREA_ACR、MEANPOT、SHRGT45、R_VALUE** —— **同一时刻的 10 个不同物理量**，被排成一条长度 10 的向量。它们的"顺序"只是论文表 2 的列举顺序，**没有任何时间含义**。

所以 `Conv1d(kernel=3)` 实际在做的是：**相邻 3 个物理量之间的交互项**（比如 TOTUSJH 和 TOTUSJZ 同源，放一起能学到组合关系）。它是一个**特征交互提取器，不是时序算子**。

| 强行套用 | 会发生什么 |
|---|---|
| **LSTM** | 把 10 个物理量当成 10 个时间步，"记住"TOTPOT 再"看"TOTUSJZ，构建一个**物理上不存在的时间依赖**。序列只有 10 步、单方向，门控机制无事可记 |
| **TCN / 因果 1D CNN** | 因果卷积意味着"位置 $i$ 不能看到位置 $j > i$"，但参数 5 和参数 9 之间没有因果次序，**强行屏蔽右半边是凭空丢信息** |
| **Transformer** | 全局注意力在长度 10 上几乎没有优势（任意两参数最大距离才 9），却要额外引入位置编码——而这里的位置编码是"第几个物理量"，**纯噪声** |
| **Mamba / SSM** | 同上，且它主打长序列（几千到几十万步），长度 10 是杀鸡用牛刀 |
| **BiLSTM-CRF** | 这是**序列标注**（给每个时间步打标签，输出标签序列），与二分类任务形态都不同 |
| **ARIMA** | 经典单变量时序预测，要求平稳性、定阶，既不吃 10 维多变量，也做不了"未来 48h 是否有事件"的二分类 |

> **判断一个模型该不该用，第一步永远是问：输入的张量里，哪个轴代表时间？**
> 我们现在的输入是 `(B, 1, 10)`，那个 10 是**特征维**不是时间维。图上所有 RNN/TCN/Mamba/ARIMA 类模型都要求那个轴是时间轴。**这一点没对齐，模型再先进也是无效复杂度。**

### 理由 3：作者是**刻意**选择简单的

论文 3.3 节原文：

> 由于在多模态混合模型中处理太阳光球纵向磁图所用到的 Swin Transformer 复杂性较高, **为了防止过拟合**, 在模型的磁场特征参数处理部分选用了一维卷积神经网络

### 理由 4：10 个参数的信息量，简单模型就能榨干

论文表 5 里有直接对照：

| 方法 | 输入 | TSS |
|---|---|---|
| Liu 等人[10] 随机森林 | **只用 10 个 SHARP 参数** | **0.829** |
| 本文 STCNet | Swin 磁图 + CNN 参数（多模态） | 0.8251 |

**一个随机森林就打平了这篇论文的多模态深度模型。** 这说明 10 个参数的信息已经饱和，换 LSTM/Mamba 在饱和特征上加复杂度，**只会过拟合**。

### 理由 5：数据集太小，越复杂的模型越吃亏

2358 个正样本、6700 条训练数据。Transformer / Mamba / ResNet1D 需要大量数据才能体现优势，这个规模下**极可能比现在的 1D-CNN 更差**。

### 那同学的提议错在哪？——他答的是另一个问题

**他的模型清单本身是对的，而且覆盖面很规范**——那是一份很好的"序列任务模型选型表"。问题在于：

> **这张表回答的是"如果任务是序列建模该用什么"，而我们的任务不是序列建模。**

### 但其中确实指出了一个真正的方向：**数据集级别的时序重构**

图里所有模型的共同前提是"输入是一段时间序列"。而我们**手里其实有时间序列的原料**——数据集文件名带时间戳，采样间隔正好 96 分钟：

```
hmi.sharp_720s.948.20111018_044800_TAI.magnetogram.fits.jpg
hmi.sharp_720s.948.20111018_062400_TAI.magnetogram.fits.jpg   ← +96 min
hmi.sharp_720s.948.20111018_080000_TAI.magnetogram.fits.jpg   ← +96 min
...
```

同一个活动区 948 连续有十几张，**这就是一条天然的时间序列**。

**真正说得通的研究方向**：不再用"单张磁图 + 单时刻参数"，而是用"某活动区**过去 N 个时刻**（例如过去 24 小时 = 15 帧）的磁图序列 + 参数序列"来预报未来 48h 是否爆发。**到那一步，TCN / LSTM / Transformer / Mamba 才真的是对的选择**，而且是明确的可扩展方向（论文本身只用单帧）。

**但这不是"替换一个模块"，而是重建整个数据集**，需要处理：

- 按活动区切出时间序列片段，并处理缺失帧（实测 2011-10-19 的 14 个时刻里就缺了 2 帧）；
- 重新定义标签（"未来 48h"的锚点从"某一帧"变成"某个序列的末端"，否则会造成时间泄漏）；
- 划分要更小心：同一活动区的序列不能跨训练/测试，否则同一段演化的不同切片会同时出现在两边。

**工作量是现在的 2-3 倍，是一个独立课题。**

### 如果留在单帧设定，值得试的只有两个（且都不在图里）

| 方案 | 理由 |
|---|---|
| **① 更深的 1D-CNN / 1D-ResNet** | 保持卷积的"局部交互"归纳偏置，同时增加容量。风险低，符合论文原意 |
| **② 树模型基线（LightGBM / XGBoost）** ⭐ | **最推荐**。论文自己引用的 Liu 等人[10] 用随机森林 + 10 个 SHARP 参数做到 TSS 0.829，与论文的 0.8251 打平。加个梯度提升树是**性价比最高、最有说服力的对照实验** |

**不建议**（在单帧设定下）：LSTM / TCN / Mamba / ARIMA / BiLSTM-CRF。

### 顺带一个关键提醒：**先改数据，再换模型**

如果想用这批序列模型，正确顺序是 **先改造数据集 → 再换模型**，而不是先换模型。建议把这条写进项目组的技术路线说明，避免后续重复讨论。

| 正样本 | 147 | 196（表 4 反推为 194） |
| 负样本 | 11963 | 11852 |

两边时间段表述相同，但实测样本数不同。可能原因：

1. 论文的"48h 内 M 级及以上"标签来自作者自己的耀斑目录，我们用的是官方 `para_flare.txt` 的标签；
2. 边界日期取闭区间还是开区间不同；
3. 论文对测试集也做了少量去重/清洗，但正文说"原始数据"（应该没做）。

**我们的测试集是 147 个正样本，论文是 194-196 个。** 在 1.6 节算过，147 个正样本下单次 TSS 的抽样不确定性约 **±0.082**。所以：

> **单次运行的 0.8477 与论文的 0.8251 之间的 +0.0226 完全落在噪声范围内。**
> **而 5 种子均值 0.8321 与论文的差值仅 +0.0070，更是在噪声内。两次结论一致：不能声称"优于论文"。**

### 前提 2：**我们的训练集比论文略小**

| | 本项目 | 论文 |
|---|---|---|
| 训练集 | 正 2358 / 负 4342 | 正 2988 / 负 5073 |

差 630 个正样本，是因为我们切出 483 个作验证集（论文没有验证集）。**从"训练数据量"角度看我们处于劣势**，这反而让"指标相当"这个结果更有说服力。

### 前提 3：训练轮数不同，且论文没报告

- 我们：**14 轮**（Epoch 4 最优，早停）
- 论文：**未报告** epoch 数、早停策略、验证集设置

**这是一个重要的可复现性缺口。** 建议在后续实验报告中主动说明我们的策略（验证集 + 早停 + 阈值扫描），这本身就是对论文复现工作的贡献。

## 2.5 对比总结（可直接用于汇报）

> **结论（已按 5 种子实验更新）**：在**测试集与论文不完全相同、训练集略小（正样本少 630 个）**的前提下，本项目的 STCNet 复现达到
> **TSS = 0.8321 ± 0.0231**（5 种子均值 ± 标准差，阈值固定 0.5），
> 与论文报告的 **TSS = 0.8251** 处于**统计上不可区分的同等水平**（均值差 0.0070，论文值落在我们 95% 置信区间 [0.8034, 0.8608] 之内）。
>
> 在业务更关心的两个指标上表现均衡：**TPR = 0.9211 ± 0.0365**（论文 0.9227）、**FAR = 0.0890 ± 0.0146**（论文 0.0976，我们略低但在 1σ 内）。
>
> **两项超出论文的增量工作**：
> 1. 论文**未报告方差**（且表 5 中同一模型的 TSS 出现 0.8251 / 0.7557 / 0.7461 三个值），我们给出了 **5 种子的 `mean ± std`**，使结论可复现；
> 2. 我们报告了 **AUC = 0.9664 ± 0.0029**，并据此定位出"**TSS 的波动主要来自固定阈值 0.5，而非模型能力**"（AUC 波动仅为 TSS 的 1/9）。
>
> **必须注明的限制**：测试集正样本仅 147 个，单次 TSS 的抽样不确定性约 ±0.08（远大于 5 种子间的 std 0.0231）。因此**任何小于约 0.02 的差异都不具备统计意义**，后续若要声称"改进"，必须通过多种子 `mean ± std` 并做配对显著性检验。

```python
def set_worker_seed(worker_id: int):
    """
    为 DataLoader 的每个子进程设置独立但可复现的随机种子。

    为什么需要这个函数
    ------------------
    num_workers > 0 时，数据加载（含 RandomResizedCrop、RandomHorizontalFlip
    等数据增强）发生在【子进程】里，而子进程不会继承主进程的随机状态。
    如果不处理，每个 worker 的随机序列由操作系统决定，导致：
        - 同一个 seed 跑两次，数据增强结果不同 → 结果不可复现
        - 多种子实验的"种子差异"里混进了"worker 随机性"，方差被高估

    做法：把主进程的 seed 和 worker_id 组合，保证
        同一次运行内各 worker 不同（避免增强撞车），
        不同运行间同种子可复现（满足实验要求）。

    Parameters
    ----------
    worker_id : int
        PyTorch 自动传入的 worker 编号（0, 1, 2, ...）。
    """
    import numpy as _np
    import random as _random
    import torch as _torch

    # 取主进程当前的种子（set_seed 已设过），与 worker_id 组合
    base_seed = _torch.initial_seed()
    worker_seed = (base_seed + worker_id) % (2 ** 32)

    _random.seed(worker_seed)
    _np.random.seed(worker_seed)
    _torch.manual_seed(worker_seed)


def get_device(prefer=None) -> torch.device:
```

## 3.9 新建 `scripts/aggregate_seeds.py`——汇总 mean ± std

> 这是**新文件**，直接创建即可。作用是读入所有 `*_seed*_metrics.json`，算 `mean ± std`，并做显著性检验的建议。

```python
"""
----------------------------------------------------------------------
scripts/aggregate_seeds.py
汇总多种子实验的结果：mean ± std + 每个种子的明细

用法（在项目根目录运行）：
    python scripts/aggregate_seeds.py                     # 汇总全部
    python scripts/aggregate_seeds.py --pattern "stcnet_seed*"
    python scripts/aggregate_seeds.py --out experiments/reports/seed_summary.md

输入：experiments/reports/*_metrics.json（由 main.py test 生成）
输出：终端表格 + 可选的 markdown 文件
----------------------------------------------------------------------
"""

from __future__ import annotations

import argparse
import json
import re
import statistics as st
from pathlib import Path

PROJECT_ROOT = Path(__file__).parent.parent.resolve()
REPORTS_DIR = PROJECT_ROOT / "experiments" / "reports"

# 要汇总的指标
METRICS = ["tss", "tpr", "tnr", "far", "precision", "f1", "accuracy", "hss", "auc"]


def load_runs(pattern: str) -> dict:
    """
    读入所有匹配的 metrics.json，返回 {seed: metrics_dict}。

    seed 从文件名里解析，例如 20261016_010203_stcnet_seed3_metrics.json → 3
    """
    runs = {}
    for f in sorted(REPORTS_DIR.glob("*_metrics.json")):
        if not re.search(pattern.replace("*", ".*"), f.name):
            continue
        m = re.search(r"seed(\d+)", f.name)
        if m is None:
            continue                      # 没有 seed 标记的跳过
        seed = int(m.group(1))
        with open(f, "r", encoding="utf-8") as fh:
            runs[seed] = json.load(fh)
    return runs


def main():
    ap = argparse.ArgumentParser(description="多种子实验结果汇总")
    ap.add_argument("--pattern", type=str, default="stcnet_seed*",
                    help="文件名匹配模式（默认 stcnet_seed*）")
    ap.add_argument("--out", type=str, default=None,
                    help="同时输出 markdown 文件到该路径")
    args = ap.parse_args()

    runs = load_runs(args.pattern)
    if not runs:
        print(f"[错误] 在 {REPORTS_DIR} 下没找到匹配 '{args.pattern}' 的 metrics.json")

        return 1

    seeds = sorted(runs.keys())
    print("=" * 92)
    print(f"多种子实验汇总 | 匹配模式: {args.pattern} | 共 {len(seeds)} 个种子: {seeds}")
    print("=" * 92)

    # ---------- 明细表 ----------
    header = f"{'seed':>5} | " + " ".join(f"{m:>9}" for m in METRICS)
    print(header)
    print("-" * 92)
    for s in seeds:
        r = runs[s]
        row = f"{s:>5} | " + " ".join(f"{r.get(m, float('nan')):>9.4f}" for m in METRICS)
        print(row)

    # ---------- 统计量 ----------
    print("-" * 92)
    print(f"{'mean':>5} | " + " ".join(
        f"{st.mean(runs[s].get(m, 0) for s in seeds):>9.4f}" for m in METRICS))
    print(f"{'std':>5} | " + " ".join(
        f"{st.stdev([runs[s].get(m, 0) for s in seeds]) if len(seeds) > 1 else 0:>9.4f}"

    print(f"{'min':>5} | " + " ".join(
        f"{min(runs[s].get(m, 0) for s in seeds):>9.4f}" for m in METRICS))
    print(f"{'max':>5} | " + " ".join(
        f"{max(runs[s].get(m, 0) for s in seeds):>9.4f}" for m in METRICS))
    print("=" * 92)

    # ---------- 重点指标 ----------
    print()
    print("【重点指标】")
    for m in ["tss", "tpr", "far"]:
        vals = [runs[s].get(m, 0) for s in seeds]
        if len(vals) > 1:
            mean, sd = st.mean(vals), st.stdev(vals)
            print(f"  {m.upper():>4}: {mean:.4f} ± {sd:.4f}   "
                  f"(95% 置信区间约 [{mean - 1.96 * sd / len(vals) ** .5:.4f}, "
                  f"{mean + 1.96 * sd / len(vals) ** .5:.4f}])")
        else:
            print(f"  {m.upper():>4}: {vals[0]:.4f}  （只有 1 个种子，无法算 std）")

    print()
    if len(seeds) < 3:
        print("⚠️  建议至少 3 个种子（推荐 5 个）才能得到可靠的 std 估计。")

    # ---------- 可选输出 markdown ----------
    if args.out:
        out = Path(args.out)
        out.parent.mkdir(parents=True, exist_ok=True)

                 "| " + " | ".join(["seed"] + [m.upper() for m in METRICS]) + " |",

        for s in seeds:

        out.write_text("\n".join(lines) + "\n", encoding="utf-8")
        print(f"[输出] markdown 汇总已保存: {out}")
```

# 第四部分 · 扩大数据集能否解决噪声问题？推荐哪些数据集？

## 4.1 先拆解："噪声"其实是 4 种不同的东西，扩大数据只能解决其中 2 种

这是一个容易混淆的问题。我们遇到的"噪声"至少包含四层：

| 类型 | 具体表现 | 扩大数据能解决吗？ |
|---|---|---|
| **① 评估噪声（方差）** | 测试集只有 147 个正样本，TSS 不确定性 ±0.082；验证集 483 个正样本，波动极差 0.184 | ✅ **能，且是最直接的收益**。标准误 ∝ 1/√N |
| **② 训练数据不足** | 2358 个正样本 vs 2763 万参数，Epoch 4 后就开始过拟合 | ✅ **能，能实质性缓解过拟合** |
| **③ 标签噪声** | "48h 内 ≥M 级"这个标签本身有物理模糊性（见 4.2） | ⚠️ **部分能**。更多样本能稀释标签错误的影响，但**不改变标签定义本身的模糊性** |
| **④ 数据固有噪声（不可约误差）** | 光球磁场与 48h 后的耀斑之间不是确定性关系，存在物理上限 | ❌ **不能**。这是问题的天花板，任何数据和模型都无法突破 |

**关键结论**：

> **扩大数据集能解决 ① 和 ②，能部分缓解 ③，但无法突破 ④。**
>
> 而我们现在最紧迫的问题恰恰是 **①（评估噪声太大，什么都证明不了）**，所以**扩大数据是正确方向**——但要说清楚它能带来什么、不能带来什么。

## 4.2 第 ③ 类噪声：标签本身的模糊性（这一层最容易被忽略）

这是需要项目组重点讨论的一点。"48 小时内是否发生 M 级及以上耀斑"这个标签有三重模糊：

**模糊 1：48 小时窗口内的任意时刻**
不管耀斑发生在第 1 小时还是第 47 小时，标签都是 1。但物理上，观测时刻与耀斑发生的间隔越远，磁图里的前兆信号越弱。**把"1 小时后爆发"和"47 小时后爆发"当成同一个正类，本身就是在往标签里注入噪声。**

**模糊 2：活动区的"归属"问题**
一个耀斑可能在两个相邻活动区之间发生，归属哪个 AR 存在人为判断。

**模糊 3：只区分 M/X 级 vs 更小**
C 级耀斑对地球影响小，但它们和 M 级的物理过程是连续的。**"是否达到 M 级"是一条人为画的线**，靠近这条线的样本标签本质上是不可靠的。

> **这一层无法靠"扩大数据"解决，但可以靠"换标签定义"解决**，比如：
> - 改成**回归任务**（预测耀斑峰值流量的对数），避免画线；
> - 或用**多分类**（B/C/M/X 分级），保留等级信息；
> - 或**缩短预测窗口**（48h → 24h），让"距离耀斑的远近"更集中，降低模糊 1 的影响。
>
> **这些是方法层面的改进，值得作为项目的一个备选研究方向。**

## 4.3 第 ④ 类噪声：物理天花板（要如实告诉项目组）

文献里 24-48h 耀斑预报在同类数据上的 TSS 普遍在 **0.8 ~ 0.9**。我们的 0.8477 已经在这一区间的中上部。

**这不是"模型还不够强"，而是"光球磁场能提供的信息就这么多"**。扩大数据、换模型都无法显著突破这个上限。**如果目标是"把 TSS 从 0.85 提到 0.95"，那这个目标本身不现实**，建议在项目目标设定上就对齐这一点。

## 4.4 推荐的数据集（公开候选）

### ⭐ 首选：SWAN-SF（Space Weather Analytics for Solar Flares）

**为什么最推荐它**：

1. **它直接对应我们最担心的方法论问题**。SWAN-SF 的原始论文标题就是
   [*How to Train Your Flare Prediction Model: Revisiting Robust Sampling of Rare Events*](https://doi.org/10.3847/1538-4365/abec88)，
   论文明确指出：**滑动窗口造成的"时间连贯性"如果不当处理，会虚假地抬高模型性能**（原文：*"lack of proper understanding of this effect may spuriously enhance models' performance"*）。
   **这正是我们在多种子实验里要防范的同类问题。**
2. **它已经划分好了 5 个时间段分区（time-segmented partitions）**，从数据集层面就防住了时间泄漏——比我们自己切分更规范、更有说服力。
3. **它是多变量时间序列（MVTS）数据集**，天然支持我们前面讨论的"时序重构"方向。

**规格**（据官方论文）：

| 项目 | 值 |
|---|---|
| 内容 | 4,098 个活动区的多变量时间序列（MVTS） |
| 参数 | **51 个**耀斑预测参数（我们是 10 个） |
| 时间范围 | **2010 年 5 月 ~ 2018 年 12 月**（与 SOLAR-STORM2 高度重叠） |
| 耀斑报告 | 集成 10,000+ 条耀斑记录 |
| 类别不平衡 | M/X 级：负样本 = **60 : 1**；X 级：**800 : 1** |
| 数据结构 | 5 个时间段分区（partition） |
| 获取 | Harvard Dataverse：[doi:10.7910/DVN/EBCFKM](https://doi.org/10.7910/DVN/EBCFKM) |
| 原始论文 | Angryk et al., *Scientific Data* 7:227 (2020)，[doi:10.1038/s41597-020-0548-x](https://doi.org/10.1038/s41597-020-0548-x) |
| 后续论文 | Ahmadzadeh et al., *ApJS* 254:23 (2021)，[doi:10.3847/1538-4365/abec88](https://doi.org/10.3847/1538-4365/abec88) |

**⚠️ 重要的取舍：SWAN-SF 是参数数据集，不含磁图。** 这意味着：

- ✅ 可以直接用于**参数分支**的实验（换 LSTM/TCN/Mamba 在这里才有意义，因为它是真序列！）
- ❌ **不能直接用于我们的 Swin 磁图分支**——我们的多模态模型需要图像

**所以 SWAN-SF 的定位是**：做"参数分支"的独立研究和对照实验，或者作为**时序重构路线的起点**。

**⚠️ 另一个必须注意的坑**：SWAN-SF 用**滑动窗口**构造样本，**相邻样本高度重叠**。已有文献专门提醒：
> *"Because of the sliding-window methodology used for SWAN-SF, caution must be taken when dealing with the temporal coherence..."*

**用的时候必须按它给的 5 个分区来划分，绝不能随机划分**，否则会重演"时间泄漏导致指标虚高"的问题。

### 备选 1：SOLAR-STORM1

同一工作组（空间环境预警和AI技术跨学科创新工作组）的前代数据集（Xin et al. 2018, ApJ 856:7），是论文引用的 [16] 的姊妹工作。**和 SOLAR-STORM2 同源同格式，接入成本最低**，但时间跨度更早（2010-2015 左右）、样本更少。适合做**跨数据集泛化性测试**（在 STORM2 训练、在 STORM1 测试），这是一个很有说服力的实验。

### 备选 2：SWAN-SF 的 EUV 扩展

近年有工作把 SDO/AIA 的 EUV 图像加入 SWAN-SF（"An EUV Extension to the SWAN-SF Flare Forecasting Dataset"，见 [SHINE 会议页](https://helioshine.org/an-euv-extension-to-the-swan-sf-flare-forecasting-dataset/)）。**如果这个数据集已公开，它对我们的价值最大**——因为它同时有**图像 + 序列参数**，正好补上 SWAN-SF 缺图像的短板。建议**优先去核实它的公开状态**。

### 备选 3：新型数据集（2025-2026，需核实）

检索中看到几篇新工作，可能提供更现代的数据集，**建议项目组分工去核实可获取性**：

- *Solar Situation Awareness and Flare Forecasting Dataset for Operational Applications*（[Scientific Data, 2026](https://www.nature.com/articles/s41597-026-08005-5_reference.pdf)）——面向业务应用
- *SWAN-SF-V2: A Multivariate Time Series Dataset for Space Weather Data Analytics; Now with AIA and Weighted SHARP Parameters*（[arXiv:2610.04591](https://export.arxiv.org/pdf/2610.04591)）——**V2 版加了 AIA 图像和加权 SHARP 参数，如果可用，这是最理想的选择**
- *Solar Flare Prediction Dataset: SHARP Magnetic Field Parameters for Machine Learning*（Zenodo: [records/15570399](https://zenodo.org/records/15570399)）——纯参数，获取门槛低

### 备选 4：直接扩展 SHARP 参数（不换数据集）

从 **SDO/HMI JSOC** 直接下载 SHARP 数据，把参数从 10 个扩展到**全部 25+ 个 SHARP 参数**（SWAN-SF 用了 51 个）。这是**不换数据源就能扩大特征空间**的低成本方案。

### 备选 5：时间上扩展（强烈推荐，成本最低）

**最容易被忽略但最划算的一条**：不换数据集，而是**用更长的历史**。我们的数据只到 2019-01，而 SDO/HMI 至今仍在运行。把 2019 年之后的 SHARP 数据和磁图接进来，可以让样本量翻倍。代价是要自己跑下载和预处理流程（这部分代码我们已经有了框架）。

# 第六部分 · 导师意见回应：交叉注意力融合机制

> **导师原话**："模型这个地方可以不简单拼接，用个交叉注意力机制把特征融合在一起。"
> **对应位置**：论文图 1 流程图中红圈标注的 ⊕（融合操作）

## 6.1 结论先行：**方向正确，值得做，但有一个技术前提必须先解决**

| 判断项 | 结论 |
|---|---|
| 方向是否正确？ | ✅ **正确**。拼接（concat）是所有融合方式里最弱的一种，它只能让后续全连接层隐式地学模态间关系；交叉注意力能显式建模"**图像的哪个区域该关注哪些磁场参数**" |
| 能否提升指标？ | ⚠️ **不确定**。参数量只增加约 3-6%，在 2358 个正样本上有过拟合风险 |
| **真正的价值在哪？** | ⭐ **在可解释性，不在指标**。交叉注意力的权重可以可视化，直接回答"**哪个 SHARP 参数在磁图的哪个区域起作用**"——这是物理意义极强的分析，是论文的加分项 |
| **技术前提** | ⚠️ **必须先解决维度错配**：Swin 输出 320 维，而参数分支输出的是 **10 个 32 维**的 token。**320 vs 32 对不上，不能直接做注意力。** 见 6.2 |

## 6.2 ⚠️ 关键问题：当前代码的两路特征维度是**错配**的

这是实现交叉注意力时**第一个会撞上的墙**，必须先讲清楚。

### 现状：两路输出的形状完全不同

```python
# src/models/stcnet.py  Mynet.forward
img = self.transformer(img)              # (B, 320)        ← 已被池化成 1 个向量
text_features = self.text_cnn(tokens)    # (B, 320)        ← 也是 1 个向量
fea = torch.cat([img, text_features], 1) # (B, 640)        ← 简单拼接
```

两边都是 **(B, 320)** 的**单个向量**。**注意力的最小要求是"一组 token"，单个向量之间做注意力没有意义**（只有 1 个 query 和 1 个 key，退化成点积）。

### 好消息：两个分支内部其实都有"多个 token"，只是被池化掉了

| 分支 | 池化前的形状 | 说明 |
|---|---|---|
| **Swin 主干** | `(B, 49, 768)` | 49 = 7×7 个空间 patch token，**天然的图像 token 序列** |
| **CNN 参数分支** | `(B, 32, 10)` | 10 = 10 个参数位置，每个位置 32 维。**但 32 维太窄**（注意力头维度通常 32/64 起，这里只能勉强 1 个头） |

`src/models/swin.py` 里 `forward` 的 `self.avgpool(x)` 把 49 个 token 池化成了 1 个，**这个池化就是信息损失的地方**——交叉注意力正好可以避免它。

### 推荐方案：图像 token 作 Query，参数 token 作 Key/Value

```python
# 图像侧：保留 49 个 token（不池化）
img_tokens = swin_backbone(x)          # (B, 49, 768)

# 参数侧：把 10 个 32 维 token 升维到 768，并加上可学习的"参数身份嵌入"
param_tokens = param_cnn_features(tokens)      # (B, 10, 32)
param_tokens = self.param_proj(param_tokens)   # (B, 10, 768)
param_tokens = param_tokens + self.param_type_embed   # (B, 10, 768)  ← 让模型知道"这是第几个参数"

# 交叉注意力：每个图像 patch 去"询问"10 个磁场参数
fused = self.cross_attn(query=img_tokens, key=param_tokens, value=param_tokens)   # (B, 49, 768)
fused = fused.mean(dim=1)              # (B, 768)  ← 池化到向量

# 与参数全局特征拼接后分类
fea = torch.cat([fused, text_features], dim=1)   # (B, 768+320)
logits = self.fc_1(fea)
```

**为什么用图像 token 作 Query**（而不是反过来）：

| | Query = 图像（49 个） | Query = 参数（10 个） |
|---|---|---|
| token 数 | 49 个，够做多头注意力 | **只有 10 个，太少** |
| 物理含义 | "**磁图的这个区域，应该关注哪些磁场参数？**" ✅ 直观且可解释 | "每个参数该看图像哪里" —— 也可解释，但 token 太少 |
| 多头可行性 | 768 / 64 = 12 个头 | 32 维最多 1 个头 |

**`param_type_embed`（参数身份嵌入）是关键设计**：因为 10 个参数**没有天然的序列顺序**（这一点在 1.9 节讨论过），必须显式告诉模型"这个 token 代表 TOTUSJH 还是 R_VALUE"，否则它就退化成一个无序集合。这正好也呼应了 1.9 节的结论——**用位置编码是不对的，用"身份"编码才对**。

### 维度错配的另一个解法（如果不想改 Swin 的池化）

如果改动 Swin 的 forward 风险太大，可以用**轻量版**：把参数 token 升维后与图像向量做**单头注意力**（1 个 query 对 10 个 key）：

```python
# 图像向量 (B, 320) 作 query，参数 token (B, 10, 320) 作 key/value
q = self.q_proj(img_vector).unsqueeze(1)        # (B, 1, 320)
kv = self.kv_proj(param_tokens_320)             # (B, 10, 320)
fused, attn_weights = self.attn(q, kv, kv)      # (B, 1, 320)
```

**优点**：改动最小，且 `attn_weights` 形状是 **(B, 1, 10)**——**可以直接画成"10 个参数的权重条形图"，可解释性一眼可见**。**缺点**：只有 1 个 query，注意力表达力弱。

> **建议**：**先做轻量版（1 个 query）验证有效性和可解释性，再做完整版（49 个 query）**。这是一个零风险的递进路线。

## 6.3 实现路线（建议分 3 步，每步都可独立回滚）

| 步骤 | 改动 | 参数量增加 | 风险 | 产出 |
|---|---|---|---|---|
| **第 1 步** | 只加"轻量版单头交叉注意力"（1 query × 10 kv），替换 `torch.cat` | 约 +0.4M（`q/kv` 投影 + 输出投影） | **低** | 有效性验证 + **10 参数注意力权重图** |
| **第 2 步** | 改成多头 + 保留 49 个图像 token（需改 `swin.py` 的 forward 返回未池化的 token） | 约 +1.5M | 中 | 更强的表达力 + **49×10 的注意力热力图**（可叠加到磁图上） |
| **第 3 步** | 加 `param_type_embed` + 门控残差（保留原始 concat 路径作为 shortcut） | +少量 | 低 | 防止注意力层退化成噪声 |

**具体代码改动位置**：

| 文件 | 改动 |
|---|---|
| `src/models/swin.py` | 第 2 步需要：`SwinTransformer.forward` 增加一个 `return_tokens=False` 参数，为 True 时返回 `(B, 49, 768)` 而不是池化后的 `(B, 320)` |
| `src/models/stcnet.py` | `CNN` 类增加 `return_tokens` 支持，返回 `(B, 32, 10)` 而非 flatten 后的 `(B, 320)` |
| `src/models/stcnet.py` | 新增 `CrossAttentionFusion(nn.Module)` 类；`Mynet.__init__` 里按 `config.FUSION_TYPE`（`"concat"` / `"cross_attn_light"` / `"cross_attn_full"`）选择融合方式 |
| `config.py` | 新增 `FUSION_TYPE = "concat"`（默认保持原行为，便于消融对比） |
| `src/utils/visualization.py` | 新增 `plot_attention_weights()`，画参数注意力条形图 + 空间注意力热力图 |

> **关键设计：`FUSION_TYPE` 开关**。这样**融合方式成为一个可消融的超参**，而不是硬编码——既能保证原实验可复现，又能直接对比 `concat` vs `cross_attn`。

## 6.4 ⚠️ 实验设计：怎么证明交叉注意力真的有用（**这比实现更重要**）

有了 1.5 节的种子实验，我们现在有了**明确的验收标准**：

```
当前基线：TSS = 0.8321 ± 0.0231（5 种子，concat 融合）
验收门槛：交叉注意力版本的 5 种子均值必须满足
          TSS_new − 0.8321 > 2 × 0.0231 = 0.046
          或者：至少 AUC 有显著提升（AUC 的 std 只有 0.0029，更容易测出差异）
```

**⚠️ 必须避免的三个坑**：

| 坑 | 后果 | 避免方法 |
|---|---|---|
| **只用 1 个种子对比** | 单次结果差异可能高达 0.06（seed 2 vs seed 4 的实测差距），**完全无法区分是架构改进还是种子运气** | **必须 5 种子** |
| **只看 TSS 不看 AUC** | 1.5.4 节已证明 TSS 波动主要来自阈值。如果交叉注意力只是让概率分布偏移（类似 seed 2 的情况），TSS 变化可能是假象 | **同时报告 AUC** |
| **忘了控制参数量** | 交叉注意力会增加参数，可能是"参数变多"而非"融合变好"带来的提升 | **同时跑一个"参数等量的纯 concat 版本"作为对照** |

**建议的实验表**（每行 5 个种子）：

| 实验 | 融合方式 | 参数量 | TSS (mean±std) | AUC (mean±std) | 结论 |
|---|---|---|---|---|---|
| 基线 | `concat` | 27.64M | 0.8321 ± 0.0231 | 0.9664 ± 0.0029 | — |
| 对照 | `concat`（参数加到与下面对齐） | ~28.9M | 待测 | 待测 | 排除"参数变多"的影响 |
| **实验** | `cross_attn_light` | ~28.9M | 待测 | 待测 | 若 AUC 显著提升 → 真改进 |
| **实验** | `cross_attn_full` | ~29.2M | 待测 | 待测 | 若不如 light → 说明数据量不够，过拟合了 |

## 6.5 ⭐ 交叉注意力的最大卖点：**物理可解释性**（建议作为论文重点）

这是我认为交叉注意力**真正值得做**的理由——不是因为它能涨点，而是因为它能**讲出一个拼接做不到的故事**。

拿到 `attn_weights` 形状 `(B, 49, 10)`（完整版）或 `(B, 1, 10)`（轻量版）后，可以做三类分析：

| 分析 | 做法 | 能回答的物理问题 |
|---|---|---|
| **① 参数重要性排序** | 对空间维度和测试集求平均 → 得到 10 个参数的平均注意力权重 | "模型最依赖哪几个 SHARP 参数？" **可与论文表 2 的物理含义对照** |
| **② 参数权重 vs 耀斑等级** | 按真实耀斑等级（M / X）分组，比较注意力分布 | "预报 X 级耀斑时，模型是否更关注不同的参数？" |
| **③ 空间注意力热力图** | 把 49 个 patch 的注意力还原成 7×7 网格，**上采样叠加到原始磁图上** | "模型在看磁图的哪个区域？是不是中性线 / 强磁场区？"**这是最出图的分析** |

**为什么这些分析有价值**：

- 论文原文只说了"拼接两个特征向量然后全连接"，**没有任何可解释性分析**；
- 太阳物理领域非常看重模型的物理合理性（"它是不是学到了真的前兆信号，还是只拟合了统计相关性"）；
- 如果我们能证明"**模型关注强剪切区 + 依赖 TOTUSJH/TOTUSPOT 这类非势能参数**"，那就**与太阳物理的先验知识吻合**，这是很强的说服力；
- 反过来，如果注意力集中在图像边缘/噪声上，那也是一个重要发现（说明模型在用伪相关）。

> **建议**：把"**基于交叉注意力的跨模态可解释性分析**"作为论文的核心创新点来包装，而不是把"提升 TSS"作为卖点。**因为前者的结论是稳的（无论指标是否提升都能做），后者的结论依赖实验运气。**

## 7.2 ⭐⭐⭐⭐⭐ 候选 #2：时间到耀斑多任务学习（**我认为这是最佳首选**）

### 核心洞察：**我们正在扔掉一半的标签信息**

现在的标签是二分类：

```
某时刻磁图 → [48h 内是否发生 M+ 耀斑？] → 1 或 0
```

但**每个正样本身上还有一个免费的、被丢弃的数字**：**距离耀斑发生还有多少小时**（从 0.1 小时到 48 小时）。

**为什么这个信息很有价值**：

1. **它直击 4.2 节分析的第 ③ 类噪声**——"48h 窗口的模糊性"。现在"1 小时后爆发"和"47 小时后爆发"被当成同一个正类，**而物理上前者的前兆信号强得多**。让模型同时学"距耀斑还有多久"，等于把这份模糊性变成了监督信号。
2. **它是一个天然的课程学习（curriculum）信号**：接近耀斑的样本更难，模型可以学着区分"紧迫"和"不紧迫"。
3. **辅助任务能正则化主任务**——这是多任务学习的经典收益，对我们这种小数据场景特别有用。
4. **推理时可以直接输出"未来 24h / 48h 的爆发概率"**，而不是单一的二分类。**这在业务上价值极大**（空间天气预报需要的是分级预警，不是一个 0/1）。

### 具体做法

```
主任务  : 二分类（48h 内是否 M+）        → 输出 (B, 2)
辅助任务: 回归"距最近 M+ 耀斑的小时数"    → 输出 (B, 1)
          对负样本，设为目标 = 48（或用一个"无耀斑"标记）

总损失 = CE(主任务) + λ₁ · SupCon + λ₂ · MSE_or_Huber(辅助任务)
```

**⚠️ 关键难点：需要重建标签**。当前 `para_flare.txt` 只有 0/1，**没有"距耀斑多少小时"这个字段**。要拿到它需要：

- 从 **NOAA GOES 耀斑目录**（或 HELIO / SolarSoft 的耀斑清单）按活动区+时间匹配，计算每个正样本到"最近的 ≥M 级耀斑"的时间差；
- 这一步需要下载外部耀斑目录并做时间/活动区匹配——**我们数据里的文件名带了活动区号和精确时间，匹配是可行的**。

**评价**：**这是我最推荐的创新点**。它既利用了被丢弃的监督信息（有理论深度），又能输出业务上更有用的分级概率（有应用价值），而且**不依赖新数据集**（现有数据 + 公开耀斑目录即可）。

## 7.4 ⭐⭐⭐⭐ 候选 #4：跨模态对比学习（**充分利用活动区的时间结构**）

### 核心洞察：现在的 SupConLoss 用法太弱

```python
# 当前实现（src/train/trainer.py）
supcon = SupConLoss(temperature=config.supcon_temperature)
loss_con = supcon(fea, labels=labels)     # 只用标签构造正负对
```

它只用了**标签**来构造正负对（同类样本互相靠近）。但我们**手里有更强的结构信息**：数据集文件名带活动区号和时间戳，**同一活动区的连续观测是天然的正样本对**。

### 三种更强的正样本对构造

| 构造方式 | 含义 | 可学到什么 |
|---|---|---|
| **① 同一活动区、时间相邻** | `hmi.sharp_720s.948.20111018_044800` 与 `..._062400` | **活动区的时序不变性**（同一个活动区在 96 分钟内的磁场结构应该相似） |
| **② 同一活动区、不同时刻** | 同一 AR 在整个演化过程中的任意两帧 | **活动区的"身份"表征**，与耀斑发生与否无关 |
| **③ 同一活动区、耀斑前后** | 爆发前 vs 爆发后的磁图 | **瞬变前兆信号**（这才是真正与耀斑相关的部分）⭐ 最有价值 |

**③ 是最有价值的**：把同一活动区"耀斑前"和"耀斑后"的磁图作为**负样本对**（应该远离），就能强迫模型学习"**到底是什么变了**"——这正是耀斑前兆的物理本质。

### 具体做法

```python
# 在 Dataset 里额外返回 (活动区号, 时间戳)，然后在 collate/训练循环里构造 pair
# 方案 A：batch 内挖掘（简单，不需要改 Dataset 结构）
for i, j in combinations(range(B), 2):
    if ar[i] == ar[j]:                        # 同一活动区
        if abs(t[i] - t[j]) < 6h:
            pair_type[i, j] = "temporal_pos"   # 时序正样本
        elif label[i] != label[j]:
            pair_type[i, j] = "pre_post_neg"   # 耀斑前后，负样本对

# 方案 B：离线构造三元组（更可控，但需要预处理）
```

**⚠️ 与 1.9 节的一致性**：这个方案**不是"把 10 个参数当序列"**，而是**利用活动区的时间结构来改进对比学习的监督信号**——两者完全不同。前者是错的（参数无序），后者是对的（活动区确实有演化）。

## 7.5 ⭐⭐⭐⭐ 候选 #1：阈值选择 + 概率校准（**最便宜、依据最硬**）

见 1.5.4 节的分析。**这个候选的依据是实测数据**：

```
AUC  = 0.9664 ± 0.0029（阈值无关，极稳）
TSS  = 0.8321 ± 0.0231（依赖阈值 0.5，波动 9 倍）
    → seed 2 是典型例子：AUC 正常（0.9641）但 TSS 最低（0.7936），
      因为它的概率分布整体偏低，被 0.5 切得偏保守
```

**做法**（必须避免测试集泄漏）：

```
1. 在【验证集】上扫阈值，选 TSS 最优的阈值 t*
2. 用 t* 固定评估【测试集】
3. 对 5 个种子分别做，报告 t* 的分布 + 测试集指标的 mean ± std
```

**预期**：**均值上升 + std 下降**（因为每个种子都用了适合自己的阈值）。

**顺带可以做概率校准**（候选 #6）：温度的缩放（temperature scaling）、Platt scaling、isotonic regression。**校准对空间天气预报有实际业务价值**——预报员需要的是"**概率是可信的**"（说 70% 就该有 70% 的频率发生），而不是排序正确。

## 7.6 ⭐⭐⭐ 候选 #5：物理先验的参数分组编码

### 核心洞察：10 个参数不是平等的，它们有物理分组

论文表 2 的 10 个参数可以按物理本质分组：

| 物理类别 | 参数 | 个数 |
|---|---|---|
| **电流 / 螺度类** | TOTUSJH, TOTUSJZ, ABSNJZH, SAVNCPP | 4 |
| **磁通量类** | USFLUX, R_VALUE | 2 |
| **能量 / 面积类** | TOTPOT, MEANPOT, AREA_ACR | 3 |
| **剪切结构类** | SHRGT45 | 1 |

**做法**：不用"10 个 token 顺序卷积"，而是：

```
① 按物理类别分组编码（4 组）→ 每组内部做注意力/卷积 → 组间再融合
② 或：在交叉注意力里给同一组的参数共享 key/value 投影
```

**价值**：这是**物理信息引导的网络设计（physics-informed）**，在太阳物理领域很受欢迎，且容易讲出故事——"**我们不是让模型盲目学 10 个输入的顺序，而是按物理意义分组**"。

**风险**：分组是人为的，需要做消融证明分组有效（随机分组 vs 物理分组的对比）。

## 7.7 ⭐⭐⭐⭐ 候选 #7：时序重构（**潜力最大，但依赖数据**）

见 1.9 节末尾的详细讨论。**要点**：用"过去 N 帧"替代"单帧"，这才是 TCN/LSTM/Transformer/Mamba **真正适用**的场景。

**⚠️ 更新建议**：**强烈建议等 JW-FD 到位后再做**。理由：JW-FD 有 199 万张磁图，时序片段的样本量才够（我们现在的 7.4 万张切完时序片段后会更少）；而且 JW-FD 跨 15 年，时序演化的多样性更好。

## 7.8 ❌ 明确不建议的方向（避免走弯路）

| 方向 | 不建议的理由 |
|---|---|
| 把参数分支换成 LSTM/TCN/Mamba/ARIMA/BiLSTM-CRF | 见 1.9 节：只占 0.37% 参数，且 10 维无时序结构。**除非先做 #7 时序重构** |
| 换更大的主干（Swin-Base / Swin-Large） | 参数从 2763 万涨到 8810 万+，在 2358 正样本上会严重过拟合。**JW-FD 到位后可重新评估** |
| 堆叠更多模态（加 EUV 图像等） | 数据量不支持；且我们的瓶颈不是模态数量，是样本量 |

| 在测试集上调阈值然后报告 | ⚠️ **这是数据泄漏**，指标虚高，审稿人一定会指出来 |
